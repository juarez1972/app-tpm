# HOTP Module — Two-Factor Authentication for Systems

This module is the reference implementation of **Layer 2 (HOTP/TOTP Authentication)** in the hybrid Zero Trust architecture described in the article above. It provides a minimal, fully functional HOTP/TOTP client-server pipeline using [FastAPI](https://fastapi.tiangolo.com/) on the server side and [pyotp](https://pyauth.github.io/pyotp/) on both sides for software-based OTP generation. It is designed as a software baseline for local testing; in production deployments, the OTP secret is stored inside a TPM 2.0 NVRAM slot and HOTP is computed entirely in hardware via `tpm2-pytss`, so the key never leaves the chip.

## 1. Background: HOTP and TOTP

### Standards

| Standard | RFC | Description |
|---|---|---|
| HMAC | [RFC 2104](https://datatracker.ietf.org/doc/html/rfc2104) | Keyed-hash message authentication code using SHA-1 |
| HOTP | [RFC 4226](https://datatracker.ietf.org/doc/html/rfc4226) | HMAC-based One-Time Password — counter-synchronized |
| TOTP | [RFC 6238](https://datatracker.ietf.org/doc/html/rfc6238) | Time-based One-Time Password — HOTP with a time-derived counter |

### Mathematical Basis

**HOTP** ([RFC 4226](https://datatracker.ietf.org/doc/html/rfc4226), [Wikipedia](https://en.wikipedia.org/wiki/HMAC-based_one-time_password)) derives a short numeric code from a shared secret `K` and a monotonically increasing counter `C`:

```
HOTP(K, C) = Truncate(HMAC-SHA-1(K, C))
```

- `K` — shared secret (Base32-encoded in this implementation, generated by `pyotp.random_base32()`)
- `C` — 8-byte counter value (big-endian)
- `HMAC-SHA-1(K, C)` — produces a 20-byte digest
- `Truncate()` — dynamic offset extraction producing a 4-byte string, then modulo 10^6 for a 6-digit code

**TOTP** ([RFC 6238](https://datatracker.ietf.org/doc/html/rfc6238), [Wikipedia](https://en.wikipedia.org/wiki/Time-based_one-time_password)) replaces the counter with a time-step value derived from the current Unix time:

```
TOTP(K, T) = HOTP(K, T)

where:
    T  = floor((CurrentUnixTime - T0) / X)
    T0 = 0  (Unix epoch)
    X  = 60  (time step in seconds — configured in this module)
```

The default TOTP time step is 30 seconds ([RFC 6238](https://datatracker.ietf.org/doc/html/rfc6238)); this module uses **60 seconds** to reduce verification load on edge devices.

### pyotp Implementation

[pyotp](https://pyauth.github.io/pyotp/) ([GitHub](https://github.com/pyauth/pyotp)) is a Python library that provides compliant HOTP and TOTP implementations. In this module:

- The server generates the shared secret with `pyotp.random_base32()` at startup.
- The server verifies codes with `pyotp.TOTP(OTP_SECRET, interval=60).verify(otp_code)`.
- The client generates codes with `pyotp.TOTP(OTP_SECRET, interval=60).now()`.

In hardware-backed production deployments (Layer 2 in the architecture), `pyotp` is replaced by a call to `tpm2-pytss` that requests the HMAC computation from the TPM's restricted keyed-hash object stored in NVRAM, as described in the root README and the article.

## 4. Running the Server

Start the server from the repository root:

```bash
python hotp/Server/server.py
```

The server binds to `0.0.0.0:5000` and is accessible from other devices on the same local network via the host machine's IP address on port 5000.

On startup, the server prints the dynamically generated OTP secret to the console:

```
DEBUG: Secret para o cliente: ABCDE2FGHIJK3LMN...
```

Copy this value — you will need it for the client in §5.

Alternatively, once the server is running, call the `/setup` endpoint to retrieve the secret programmatically:

```bash
curl http://127.0.0.1:5000/setup
```

## 5. Running the Client

Open `hotp/Client/client.py` and set the `OTP_SECRET` variable to the value obtained from the server in §4:

```python
OTP_SECRET = "ABCDE2FGHIJK3LMN..."   # replace with the value from the server
```

Then run the client:

```bash
python hotp/Client/client.py
```

The client logs in via `POST /login`, receives a session token, and then enters a loop that sends a new TOTP code to `POST /verify` every 60 seconds.

## 6. API Endpoints

| Method | Path | Description | Request Body | Success Response |
|---|---|---|---|---|
| `GET` | `/setup` | Returns the OTP secret and configuration for client bootstrapping | — | `{"user": "...", "otp_secret": "...", "interval": "60s"}` |
| `POST` | `/login` | Authenticates with username/password; returns a session token | `{"username": "...", "password": "..."}` | `{"session_token": "...", "message": "..."}` |
| `POST` | `/verify` | Validates the current TOTP code against the active session | `{"token": "...", "otp_code": "..."}` | `{"status": "valid", "message": "Conexão mantida."}` |

All error responses follow FastAPI's standard `HTTPException` format: `{"detail": "..."}`.

## 7. Authentication Flow

```
Client                                  Server
  |                                       |
  |-- POST /login {username, password} -->|
  |                                       | validate credentials
  |<----------- {session_token} ----------|
  |                                       |
  |   (loop every 60 seconds)             |
  |                                       |
  |-- POST /verify {token, otp_code} ---->|
  |                                       | totp.verify(otp_code)?
  |                                       |   YES --> session kept
  |<------ {status: "valid"} -------------|
  |                                       |
  |-- POST /verify {token, otp_code} ---->|
  |                                       |   NO  --> active_sessions.remove(token)
  |<------ HTTP 401 (OTP invalid) --------|
  |                                       |
  | (client exits)                        |
```

**Key implementation details:**

- `active_sessions` is an in-memory Python `set`; sessions do not survive a server restart.
- Session tokens are generated with `secrets.token_hex(16)` (128-bit entropy, cryptographically secure).
- The TOTP time step is set to `interval=60` on both the server and client — both sides must use the same value.
- The `/setup` endpoint exposes the OTP secret in plaintext and is intended for local development only.

## 8. Test Scenarios

| Scenario | How to reproduce | Expected result |
|---|---|---|
| Normal operation | Run server, set `OTP_SECRET` in client, run client | Client prints `[+] Servidor confirmou: Sessão Ativa.` every 60 s |
| OTP mismatch (forced failure) | In `client.py`, change the `otp_atual` variable to a fixed wrong value (e.g., `"000000"`) | Server returns HTTP 401, removes token from `active_sessions`, client prints session-terminated message and exits |
| Cross-device test | Run server on one machine; set `URL` in `client.py` to `http://<server-ip>:5000`; run client on another machine | Same as normal operation — server accepts connections from any host on the LAN |
| Secret mismatch | Use a different `OTP_SECRET` in the client than what the server generated | Every `/verify` call returns HTTP 401 immediately |

## 9. Security Considerations

### Production Hardening

The server contains three hardcoded values that **must** be replaced with environment variables before any production or shared-environment deployment:

```python
# Replace these hardcoded values:
FIXED_USER = "cliente-otp"
FIXED_PASS = "senha-aleatoria-123"
OTP_SECRET = pyotp.random_base32()  # regenerated at every restart — not persisted
```

Recommended approach:

```bash
export HOTP_USER="<strong-username>"
export HOTP_PASS="<strong-password>"
export HOTP_SECRET="<pre-shared-base32-secret>"
```

```python
import os
FIXED_USER = os.environ["HOTP_USER"]
FIXED_PASS = os.environ["HOTP_PASS"]
OTP_SECRET = os.environ["HOTP_SECRET"]
```

### TPM Delegation (Layer 2)

This module uses `pyotp` (software) as a testing baseline. In the full architecture described in the article, **Layer 2** delegates HOTP computation to TPM 2.0 hardware via `tpm2-pytss`. The OTP secret is stored as a *Restricted Keyed-Hash* in TPM NVRAM with `fixedtpm` and `fixedparent` attributes, making it non-exportable. A monotonic counter in NVRAM provides hardware-enforced rollback protection. See the root README for the complete `tpm2-pytss` code example.

### Session Management

- Sessions are stored in an in-memory `set` (`active_sessions`). A server restart silently invalidates all active sessions.
- There is no session expiry by time — a valid token persists until an OTP failure or a server restart.
- For production use, replace the in-memory `set` with a persistent store (e.g., Redis) and add TTL-based session expiry.

### Brute-Force Protection

The current implementation has no rate limiting on `/login` or `/verify`. Before exposing the server on any non-loopback interface in a production environment:

- Add rate limiting (e.g., `slowapi` for FastAPI).
- Add account lockout after N consecutive OTP failures.
- Restrict `/setup` to localhost or remove it entirely after initial provisioning.
- Consider this threat under [MITRE ATT&CK T1078 (Valid Accounts)](https://attack.mitre.org/techniques/T1078/), which describes credential abuse risks that this module's TOTP layer partially mitigates.

### Network Exposure

The server binds to `0.0.0.0` intentionally for local-network testing. In production, place it behind a ZTNA gateway (OpenZiti or Twingate, as described in Layer 4 of the architecture) rather than exposing it directly. TLS termination is not included in this module; the `antigos/` directory contains earlier SSL experiments (`ssl-server.py`, `ssl-client.py`) that can serve as reference.
